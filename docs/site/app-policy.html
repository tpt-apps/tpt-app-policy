The problem

Approval rules live in spreadsheets, in people's heads, and in code that only one person understands. A decision made last year cannot be explained today, and a change to a limit can be made without anyone seeing it.

How it works

1. Write the rules

Plain YAML: a rule names a field, a condition, and a decision.

2. Send a request

A JSON file, a line on standard input, or a request to the local HTTP service.

3. Get the decision

Approved, review, approval required or rejected, with the approvers and the rules that matched.

4. Keep the record

A fixed output format, a hash of the input, and the policy version. The same input always gives the same output.

Example

A rule file for expense claims:

policy: expense
version: "1.0.0"

rules:
  - id: manager-approval
    description: Expenses over $1,000 need manager approval
    when:
      expense.amount:
        gt: 1000
    then:
      decision: approval_required
      approver: manager

  - id: finance-approval
    description: Expenses over $5,000 also need finance approval
    when:
      expense.amount:
        gt: 5000
    then:
      decision: approval_required
      approver: finance

Running tpt-policy explain on a $6,200 claim prints:

decision: approval_required
policy: expense@1.0.0
approvers: manager, finance
matched rules: manager-approval, finance-approval

explanations:
  manager-approval (approval_required): Expenses over $1,000 need manager approval
  finance-approval (approval_required): Expenses over $5,000 also need finance approval

The same decision can be written as a single HTML page with --format html, for a file or an email attachment.

Features

  • Conditions on nested fields: equals, not equals, greater or less than, in a list, contains, exists, and AND, OR and NOT.
  • Clear errors. A broken rule file says what is wrong, where (the line), why, and how to fix it.
  • Inline tests in the rule file, run with one command, so you can check a change before it goes live.
  • Runs offline. No account, no keys, no phone-home. The privacy statement is in the documentation.
  • Stable exit codes, so a script or a build can act on the decision.
  • A local HTTP service, for systems that ask for decisions over the network. It listens on localhost by default, with an optional token.
  • A Docker image for running it in a container.

FAQ

Does it send my data anywhere?
No. It reads the files you give it and writes its output to your folder. It makes no network calls.

Do I need a licence key?
No. There is nothing to activate.

What if a rule matches nothing?
The policy's default decision applies. It is review unless you set another default, so a gap in the rules fails safe.

Is this a compliance certification?
No. It makes decisions from the rules you write. It does not certify that you comply with any law or standard.

Can it replace my approval workflow system?
No. It gives the decision and the approvers. It does not send emails, route tasks, or keep a queue.
