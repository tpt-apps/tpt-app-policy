1. Executive Summary

TPT Solutions already contains a large open-source Rust ecosystem of
roughly 330 repositories. The commercial opportunity is not to turn that
ecosystem into a conventional SaaS platform. The recommended strategy is
to use the existing repositories as the technical foundation for a
family of small, professional, self-hosted applications that solve
narrow and valuable business problems.

The commercial portfolio should be built around one shared platform:

TPT Policy Core + TPT Runtime + TPT WASM/Security infrastructure

The first and most important commercial application is TPT App
Policy. The remaining products should reuse the same policy engine,
schema system, validation framework, runtime, CLI conventions,
packaging, licensing, documentation, and security model.

The products should be:

downloadable;

self-hosted;

usable without a TPT cloud account;

usable without a recurring subscription;

deterministic where practical;

automatable from a CLI;

scriptable through JSON/HTTP;

deployable as native binaries and/or containers;

useful without vendor-specific ERP integrations;

bounded enough that a solo developer can maintain them.

The central product-design principle is:

Own the rules and execution boundary; do not own the customer's
business systems.

For example, TPT App Policy should not attempt to integrate directly
with SAP, Xero, MYOB, NetSuite, Dynamics, Oracle, or every custom ERP.
It should accept structured input and return a structured decision. The
customer's existing integration layer connects those inputs and outputs
to its systems.

This dramatically reduces support requirements while preserving
commercial value.

2. Commercial Strategy

2.1 Business model

The preferred commercial model is:

Open-source infrastructure remains useful and discoverable.

Commercial products package the infrastructure into complete
business solutions.

Customers purchase perpetual licences through Gumroad.

Customers download a release bundle.

Customers run the software locally or inside their own
infrastructure.

Updates are released periodically.

Updates can be included for a defined period or permanently,
depending on SKU.

No mandatory hosted service is required.

The product should not depend on subscriptions for basic operation.

2.2 Why this model fits TPT

The existing TPT ecosystem has several properties that suit a
self-hosted commercial model:

Rust implementation;

WASM execution;

capability-oriented security;

runtime/resource management;

cryptographic primitives;

MCP/tooling infrastructure;

CLI-oriented components;

deterministic execution capabilities.

These are infrastructure-heavy capabilities that can be difficult for a
small business to build internally but can be delivered as a local
executable.

2.3 Target customer

The primary customer should be:

A small or medium business, internal IT team, developer, consultant,
or operations team that needs a reliable business-rule/data-processing
utility but does not want to build it from scratch or adopt another
SaaS platform.

Secondary customers:

software developers;

DevOps engineers;

automation consultants;

compliance teams;

security engineers;

AI application developers.

Large enterprises should not be the initial target because their
procurement, integration, security review, and support requirements
would undermine the solo-developer business model.

6. Core Design Principle: JSON Boundary

The commercial products should use structured data boundaries.

The canonical boundary should be JSON initially.

Example:

{
  "supplier": {
    "id": "SUP-123",
    "status": "active"
  },
  "amount": 7200,
  "currency": "NZD"
}

A policy returns:

{
  "decision": "approval_required",
  "rules_triggered": [
    "require-approval"
  ]
}

This boundary is critical.

It means the product does not need native knowledge of:

SAP;

Oracle;

NetSuite;

Xero;

MYOB;

Microsoft Dynamics;

Salesforce;

custom ERPs;

proprietary databases.

The customer's existing application or integration system is responsible
for translating its native representation into the TPT input format.

7. TPT Policy Core

7.1 Purpose

The Policy Core is the central commercial capability.

It evaluates structured input against deterministic rules and produces a
structured decision.

7.2 Example policy

policy: purchase-order

rules:

  - name: require-approval
    when:
      amount:
        gt: 5000
    then:
      decision: approval_required

  - name: block-supplier
    when:
      supplier.status:
        equals: blocked
    then:
      decision: rejected

  - name: require-three-quotes
    when:
      amount:
        gt: 10000
    then:
      decision: approval_required
      requirement: three_quotes

7.3 Evaluation model

A policy should produce:

decision;

matched rules;

failed checks;

warnings;

requirements;

structured explanation;

optional audit information.

Example:

{
  "decision": "approval_required",
  "matched_rules": [
    "require-approval"
  ],
  "requirements": [
    "manager_approval"
  ],
  "policy_version": "1.2.0"
}

7.4 Determinism

Where practical, the engine must be deterministic.

Given:

same input
+
same policy
+
same policy version
+
same configuration

the engine should produce the same result.

This makes it appropriate for:

compliance;

auditing;

financial validation;

approvals;

automated workflows.

14. TPT Approval Engine

14.1 Product statement

Define deterministic approval requirements without embedding approval
logic in every application.

Example:

approval:

  - when:
      amount: "<1000"
    decision: automatic

  - when:
      amount: "1000-5000"
    approver:
      role: manager

  - when:
      amount: ">5000"
    approver:
      role: director

14.2 Important boundary

The engine determines:

Who or what must approve.

It does not become an email or workflow SaaS.

The customer's workflow system consumes the decision.

This keeps the product small and reliable.

35. Policy DSL Design

The DSL should prioritise readability.

Example:

policy: purchasing
version: 1

rules:

  - id: purchase-under-limit
    description: Purchases below $1,000 are automatically approved

    when:
      amount:
        lt: 1000

    then:
      decision: approved

  - id: purchase-manager
    when:
      amount:
        gte: 1000
        lt: 5000

    then:
      decision: approval_required
      approver: manager

Avoid creating a programming language.

The DSL should remain declarative.

36. Policy Testing

Policies must be testable without production systems.

Example:

tests:

  - name: small purchase
    input:
      amount: 500
    expect:
      decision: approved

  - name: large purchase
    input:
      amount: 6000
    expect:
      decision: approval_required

CLI:

tpt-policy test policy.yaml

Output:

PASS small purchase
PASS large purchase

2 tests passed

This is a high-value developer feature and a major differentiator.

52. Final Recommendation

The highest-priority commercial asset should be:

TPT App Policy --- a self-hosted, deterministic business-rule engine
with CLI, JSON, REST and WASM interfaces.

It should use the existing TPT infrastructure rather than duplicate it.

The second product should be:

TPT Data Validator

because it converts the policy/schema machinery into an immediately
understandable business utility.

The third should be:

TPT Document Validator

because it generalises the same infrastructure.

The fourth should be:

TPT Invoice Validator

because it creates a clear vertical proposition with obvious business
value.

Only after these foundations are working should the portfolio expand
into secure execution, compliance and AI-agent control.

The core commercial thesis is:

TPT provides the infrastructure. The commercial applications turn
that infrastructure into finished, useful tools that businesses can
buy once and run themselves.

This approach maximises reuse of the existing GitHub investment while
minimising recurring infrastructure, customer-specific development, and
support obligations.
